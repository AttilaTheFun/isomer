# Remote sessions (0.45)

An app's SwiftUI can run on a server, built headless, and be drawn on a
client that holds nothing of the app but a renderer: a browser with the
React renderer, an Android phone with the Compose renderer. The client
sends what the person does; the app answers with each frame as a patch of
its render tree. A low-end phone needs only the renderer and a WebSocket:
no Swift, no wasm, no native library.

```
 client (renderer only)                 server
 ┌───────────────────────┐   WebSocket  ┌─────────┐  stdio   ┌────────────────────┐
 │ React / Compose       │ ───────────▶ │ gateway │ ───────▶ │ the app, headless   │
 │ tree reader (patches) │ ◀─────────── │         │ ◀─────── │ (one run a session) │
 └───────────────────────┘  or gRPC     └─────────┘          └────────────────────┘
```

## One wire format

Every path from Isomer's SwiftUI to a renderer speaks protobuf
(shared/wire), whether the renderer is in the same process, in another on
the same machine, or across a network, and whether the stream is live or
recorded:

| File | What |
| --- | --- |
| `tree.proto` | the render tree and its patches, what a component-system renderer takes (in process since 0.45, FlatBuffers before) |
| `session.proto` | a remote session: `ClientMessage` (start, resize, events, keys, text, appearance, scene phase, URLs, back) and `ServerMessage` (a patch, a platform command, an image, a URL, the app's appearance, text input, a log line) |
| `headless.proto` | the headless driver: `Command` and `Answer` (docs/headless.md) |
| `session_service.proto` | both as gRPC services: `Session.Connect` and `Headless.Drive`, bidirectional streams |

In a stream of bytes (a pipe, a file) each message is length-delimited, as
protobuf's `writeDelimitedTo` writes them, so a session can be recorded and
replayed. Over a WebSocket each binary message is one message. The Swift
is generated by protoc-gen-swift and checked in (`IsomerSwiftUI`'s
tree.pb.swift, `IsomerWire` in shared/wire/swift), kept current by
//shared/wire's diff tests; the JavaScript and Kotlin readers and writers
are written by hand against protobuf's wire format, so the web and Android
need no protobuf library (flat_tree.js and session_messages.js,
FlatTree.kt and RemoteIsomer.kt).

## The server

The app is built headless (`--@isomer//headless`) and runs with
`ISO_HEADLESS_PROTOCOL=session`: it reads the client's messages on standard
input and writes its own on standard output
(headless/libraries/swift_ui/RemoteSession.swift). It waits for `start`
(the client's size, scale, appearance, renderer and the app's ISO_
environment), binds the renderer the client draws with (React's or
Compose's tree) and renders a frame whenever the app asks for one, at most
one a display frame. One process is one session: Isomer's runtime is one
per process.

The examples' gateway (examples/remote/gateway) runs one for each
connection:

```sh
cd examples
bazel build --@isomer//headless //headless/storybook_headless_application //remote:gateway //remote:web_test
bazel-bin/remote/gateway --app bazel-bin/headless/storybook_headless_application/storybook_headless_application \
    --site bazel-bin/external/isomer+/web/remote_client/remote_client --port 8090 --grpc-port 8091
# then http://127.0.0.1:8090/?ISO_STORYBOOK_STORY=state.observableobject
```

- `ws://<host>:<port>/session`: a remote session over a WebSocket;
- `ws://<host>:<port>/headless?ISO_…=…`: the headless driver;
- `http://<host>:<port>/…`: the files of `--site` (the web's thin client);
- gRPC on `--grpc-port`: `Session.Connect` and `Headless.Drive`
  (Headless.Drive takes the app's environment from the call's `iso_…`
  metadata).

It prints `gateway: ws://<host>:<port>/session grpc <host>:<port>` once
listening (port 0 is the system's choice).

## The clients

- **The web**: `connectIsomer({ url, container })`
  (wasm/libraries/swift_ui/runtime/remote.js): the React renderer,
  flat_tree.js and a WebSocket; the page's ISO_ query parameters are the
  app's environment. web/remote_client is a page of it (`?session=ws://…`
  names another server than the page's own).
- **Android**: `IsomerRemote(url)` (dev.isomer.runtime, with the
  interpreter: android/libraries/swift_ui/kotlin/…/RemoteIsomer.kt): the
  Compose renderer, FlatTree and IsomerWebSockets. examples/android/
  remote_android_application is an app of it: Kotlin and Compose only.

## What a remote app can't know

- **Text is measured on the server**, as the headless host measures it (a
  fixed-width estimate): the client's renderer lays the tree out with its
  own fonts, as it does in process, but what the app computes from a
  measurement (a `GeometryReader` around text) is approximate.
- **A key's answer comes too late** to keep it from a field: `.onKeyPress`
  sees every key, and the client lets every key through.
- **Back**: the client sends the system's back to the app, which can't
  answer in time for the system to act on it; an app at its root stays.
- **Images** the app makes reach the client as `image` messages; images by
  URL are the client's to load.
- **One session a process on Android** (the interpreter's one tree, as a
  WasmView's).

## Tests

In the examples, with the app's flag (`bazel test --@isomer//headless
//remote/...`), in every CI build beside the headless tests:

- `//remote:grpc_test`: `Headless.Drive` and `Session.Connect` over gRPC;
- `//remote:web_test`: the web's thin client in headless Chrome over the
  WebSocket, drawing the session and clicking in it (Chrome for Testing on
  Linux, the Mac's Chrome on a Mac).

Android's client was checked by hand on an emulator (drawn, tapped, typed
into); an automated run is open (TODO.md).
