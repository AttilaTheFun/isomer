# Features as side modules, and a mixed native/interpreted runtime (prototype)

Tooling for two measured prototypes (docs/side_modules.md has the design and
the numbers):

1. **Side modules.** A feature ships as a wasm side module of kilobytes over
   one runtime module (the Swift standard library, Foundation and Isomer's
   SwiftUI) that the app has once, instead of a reactor carrying its own copy.
   `WasmDynamicLinker` (//shared/wasm_host) loads it under WasmKit;
   `node/loader.mjs` in a browser or Node.
2. **Mixed mode.** The runtime stays one wasm module, interpreted, and native
   copies of its hot functions (wasm2c, chosen from a profile and from
   crossing counts) are compiled into the host. They share the runtime's
   memory, a mirrored function table and its stack pointer. The host enters
   native code at the runtime's entry points; native code calls back into the
   interpreter for cold functions and for the feature's code; features call a
   few heavy runtime functions natively (`ROUTED`).

Nothing here is wired into Bazel yet: it runs from a checkout with
`bazel`-built inputs, nix for Binaryen and WABT, and Node.

## Layout

| Path | What |
| --- | --- |
| `split/split_link.py` | a reactor's Bazel link (`aquery`) → `link_runtime.sh` and `link_side.sh` |
| `node/` | the dylink loader in JS (`loader.mjs`), and drivers that render, tap every first-frame tap id and write the render stream (`drive_all.mjs`, `hot_run.mjs`); `locrel_fix.mjs` is the loader-side workaround for an unpatched wasm-ld |
| `split/locrel_from_map.py` | the same workaround's slot list, from wasm-ld's `-Map` (`--emit-relocs` crashes lld on large inputs) |
| `profile/` | V8 profile readers: time by module (`prof_by_module.py`), how few functions cover the time (`hot_coverage.py`), what feature code spends its time calling (`feature_calls.py`) |
| `split/native_set.py` | the first native set: functions on profiled stacks plus direct callees (Binaryen's `--print-call-graph`) |
| `split/round.sh` | one round: split, slim, map slots, wasm2c, bridge, build, run, count crossings |
| `split/grow_set.py` | adds what native code called into the interpreter most |
| `split/pick_routed.py` | runtime functions features call that are worth a crossing (time per call) |
| `split/gen_mixed.py` | the bridge: C glue for the wasm2c module (imports, exports, per-signature calls and trampolines, memory over WasmKit's) and a WasmKit shim |
| `split/slim_native.py`, `split/map_slots.py`, `split/wasmtool.py` | the native part without data or unneeded exports; the slots the split added, mapped to the runtime's functions; wasm reading helpers |
| `host/` | SwiftPM hosts on the forked WasmKit: `SideloadCheck` (side modules under WasmKit), `RuntimeCheck` (through Isomer's `WasmKitRuntime.loadSideModule`), `MixedCheck` (mixed mode; its `CHot` target is generated by `round.sh`); `BENCH=drag` in the first and last runs the 2048 drag benchmark (`DragBench.swift`) |
| `host-original/` | `SideloadCheck` on the WasmKit pinned before (no linker): the benchmark's baseline |
| `data/` | the Storybook's native set and routed list as its rounds left them, and the set grown on 2048's drag as well (the one the 2048 numbers use) |

## Reproducing it

Every number in docs/side_modules.md comes from these steps; that document
maps each claim to one. Prerequisites: a Mac with Bazel (bazelisk), nix
(Binaryen and WABT), Node, and Xcode for the iPhone.

### 1. The patched wasm-ld

The fix is tools/patches/lld_wasm_pic_locrel.patch, also the branch
`wasm-ld-pic-locrel-6.4.2` of pawlowskialex/llvm-project (on
swift-6.4.2-RELEASE, the toolchain's own LLVM). Building lld and its tests:

```sh
git clone --filter=blob:none --no-checkout https://github.com/pawlowskialex/llvm-project llvm
cd llvm && git sparse-checkout set llvm lld cmake third-party libunwind/include
git checkout wasm-ld-pic-locrel-6.4.2
nix shell nixpkgs#cmake nixpkgs#ninja --command sh -c '
  cmake -G Ninja -S llvm -B build -DCMAKE_BUILD_TYPE=Release -DLLVM_ENABLE_PROJECTS=lld \
    -DLLVM_TARGETS_TO_BUILD=WebAssembly -DLLVM_ENABLE_ASSERTIONS=ON -DLLVM_INCLUDE_BENCHMARKS=OFF \
    -DLLVM_INCLUDE_EXAMPLES=OFF -DLLVM_ENABLE_ZSTD=OFF -DLLVM_ENABLE_ZLIB=OFF -DLLVM_ENABLE_LIBXML2=OFF \
    -DCMAKE_C_COMPILER=/usr/bin/clang -DCMAKE_CXX_COMPILER=/usr/bin/clang++
  ninja -C build lld lld-test-depends'
build/bin/llvm-lit build/tools/lld/test/wasm/     # 213 pass; shared-locrel.s fails without the fix
```

Without it, a side module still loads if the loader corrects its LOCREL slots:
node/loader.mjs does, from the module's `--emit-relocs` section (lld crashes on
large inputs with it) or from split/locrel_from_map.py's sidecar
(`<side>.wasm.locrel.json`, from wasm-ld's `-Map` and the input objects; link
the side module with `--no-gc-sections`).

### 2. WasmKit with the side-module API and cheaper host calls

pawlowskialex/WasmKit, branch `isomer-side-modules` (what MODULE.bazel pins).
Its own tests need the fixtures the archive lacks:

```sh
git clone -b isomer-side-modules https://github.com/pawlowskialex/WasmKit && cd WasmKit
python3 Vendor/checkout-dependency
swift test --filter "WasmKitTests|WASITests|WasmKitWASIThreadsTests|WasmKitGDBHandlerTests"
```

### 3. A runtime module and side modules

```sh
cd examples
bazel build -c opt //wasm/example_full_feature:example_full_release.wasm   # the Storybook
bazel aquery -c opt 'mnemonic(CppLink, deps(//wasm/example_full_feature:example_full_release.wasm))' \
  --output=jsonproto > /tmp/link.json
python3 ../tools/mixed/split/split_link.py /tmp/link.json full_reactor_release \
  libexample_full_lib.a libstorybook.a example_full_lib.autolink storybook.autolink \
  --out /tmp/linked --wasm-ld <patched wasm-ld>      # add --strip for the sizes
(cd "$(bazel info -c opt execution_root)" && sh /tmp/linked/link_runtime.sh && sh /tmp/linked/link_side.sh)
```

The same for 2048 (`//wasm/game2048_feature:game2048_release.wasm`,
`game2048_reactor_release libgame2048_lib.a game2048_lib.autolink`) and the
tap counter (`//wasm/tap_counter_feature:tap_counter_release.wasm`,
`tap_counter_reactor_release libtap_counter_lib.a tap_counter_lib.autolink`).
Sizes: `gzip -9c <file> | wc -c`.

### 4. Rendering them, and the baseline to compare with

```sh
node node/drive_all.mjs /tmp/base.bin <self-contained reactor.wasm>       # the baseline stream
node node/drive_all.mjs /tmp/side.bin /tmp/linked/runtime.wasm /tmp/linked/side.wasm
cmp /tmp/base.bin /tmp/side.bin                                            # byte-identical
(cd host && swift build -c release)                                       # WasmKit hosts
host/.build/release/SideloadCheck /tmp/wk.bin /tmp/linked/runtime.wasm /tmp/linked/side.wasm
host/.build/release/RuntimeCheck /tmp/rt.bin /tmp/linked/runtime.wasm /tmp/linked/side.wasm
```

`drive_all.mjs` taps every tap id of the first frame (the Storybook's 99
stories) and writes the whole render stream; the hosts write the same.

### 5. Where the time goes (profiles)

Link the runtime and the side module without `--strip` (names), then:

```sh
node --cpu-prof --cpu-prof-dir=/tmp/prof --cpu-prof-interval 100 node/drive_all.mjs /dev/null runtime.wasm side.wasm
python3 profile/prof_by_module.py /tmp/prof        # time by module, core machinery vs feature code
python3 profile/hot_coverage.py /tmp/prof runtime.wasm   # how few functions cover the time
python3 profile/feature_calls.py /tmp/prof         # what feature code spends its time calling
```

All of the runtime compiled to C instead (the 319 MB of C, 36 MB of code):

```sh
nix shell nixpkgs#wabt --command wasm2c --num-outputs=10 runtime.wasm -o runtime.c
WABT=$(nix shell nixpkgs#wabt --command sh -c 'dirname $(dirname $(command -v wasm2c))')
ls runtime_*.c | xargs -P 10 -I{} clang -O2 -c -w -I. -I$WABT/include {} -o {}.o
size -m runtime_*.o | grep __text
```

### 6. Mixed mode

```sh
wasm-opt --print-call-graph runtime.wasm -o /dev/null > callgraph.dot      # nixpkgs#binaryen
python3 split/native_set.py /tmp/prof callgraph.dot runtime.wasm 3 set.txt  # the first set
python3 split/slim_native.py runtime.wasm split_input.wasm \
  memory,__indirect_function_table,__stack_pointer,iso_hot_start,iso_hot_render,iso_hot_render_pending,iso_hot_event,iso_hot_resize,iso_hot_alloc,iso_hot_free,iso_hot_shutdown,iso_hot_pending_tasks,iso_hot_configure,iso_hot_set_color_scheme,@data/storybook_routed.txt
export RUNTIME=$PWD/runtime.wasm SPLIT_INPUT=$PWD/split_input.wasm SIDE=$PWD/side.wasm \
  BASELINE=/tmp/base.bin ROUTED=$PWD/data/storybook_routed.txt
split/round.sh set.txt                     # split, slim, wasm2c, bridge, build, run, count
python3 split/grow_set.py $RUNTIME /tmp/isomer-mixed/round/crossings.txt /tmp/isomer-mixed/round/slots.txt set.txt set2.txt 20
split/round.sh set2.txt                    # …until the crossings stop falling
```

`data/storybook_native_set.txt` is where the Storybook's rounds ended;
`data/storybook_2048_native_set.txt` that set grown on 2048's drag. The
routed list: `COUNT_IMPORTS=1 ROUTED=… host/.build/release/MixedCheck …`
writes `import_calls.txt`, then `split/pick_routed.py /tmp/prof
import_calls.txt 0.3 routed.txt`. `CHECKED_CALLS=1` measures the same run
through WasmKit's checked `invoke` instead of `invokeUnchecked`; `TIMING=1`
prints the time spent in the interpreter.

### 7. The 2048 drag benchmark (event → frame)

On a Mac, the three configurations (`BENCH=drag`: ten drags of 60 `changed`
events, a render after each, then each release's animation frames):

```sh
(cd host-original && swift build -c release)   # the WasmKit pinned before (5fbb9db)
BENCH=drag host-original/.build/release/SideloadCheck /dev/null game2048_release.wasm
BENCH=drag host/.build/release/SideloadCheck /dev/null runtime.wasm game2048_side.wasm
BENCH=drag ROUTED=$PWD/data/storybook_routed.txt host/.build/release/MixedCheck /dev/null \
  $RUNTIME /tmp/isomer-mixed/round/c/shim.wasm /tmp/isomer-mixed/round/slots.txt game2048_side.wasm
```

(after a `split/round.sh data/storybook_2048_native_set.txt`; `COUNT=1` adds the
crossing counts `grow_set.py` reads). On an iPhone:
examples/tools/wasm_bench/mixed_ios_app (its `prepare.sh` copies the round's
C and the modules in), then

```sh
bazel build -c opt --ios_multi_cpus=arm64 --repo_env=ISOMER_TEAM_ID=<team> \
  //tools/wasm_bench/mixed_ios_app:mixed_bench_ios_application
xcrun devicectl device install app --device <udid> <the .app>
xcrun devicectl device process launch --device <udid> --console com.LoganShire.IsomerMixedBench
```

It prints `RESULT` lines (and writes Documents/bench_output.txt): three runs
each of the reactor, the side module interpreted and the side module mixed.
The original WasmKit can't be linked beside the new one, so its "before" runs
on the new one (on the Mac the two measure the same for a reactor).

## What it measured (Storybook, 99 taps, every story's page opened)

| | Time | Native code |
| --- | --- | --- |
| Self-contained reactor, WasmKit | 3.15 s | — |
| Mixed mode | 0.44 s | 3.9 MB (7.4 MB with bounds checks) |

The render stream is byte-identical to the self-contained build's in every
configuration. Feature size: the Storybook as a side module is 226 KB gzip,
against 5.4 MB for the reactor; the runtime (6.7 MB gzip) is shipped once.

## Caveats

- The native code relies on WasmKit's guard pages without bounds checks; an
  access out of bounds in native code faults instead of trapping until
  WasmKit's trap handling covers it (the bounds-checked build doesn't).
- The set and routed list come from one workload; a function outside them
  runs interpreted, slower but correct.
- The scripts assume the Storybook's entry points and a scratch directory;
  Bazel rules are the next step.
