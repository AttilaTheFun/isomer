# Features as side modules, and a mixed native/interpreted runtime (prototype)

Tooling for two measured prototypes (docs/side_modules.md has the design and
the numbers):

1. **Side modules.** A feature ships as a wasm side module of kilobytes over
   one runtime module (the Swift standard library, Foundation and Isomer's
   SwiftUI) that the app has once, instead of a reactor carrying its own copy.
   `WasmDynamicLinker` (//shared/wasm_host) loads it under WasmKit;
   `node/loader.mjs` in a browser or Node.
2. **Mixed mode.** The runtime stays one wasm module, interpreted, and native
   copies of its hot functions (wasm2c, chosen from a profile and from
   crossing counts) are compiled into the host. They share the runtime's
   memory, a mirrored function table and its stack pointer. The host enters
   native code at the runtime's entry points; native code calls back into the
   interpreter for cold functions and for the feature's code; features call a
   few heavy runtime functions natively (`ROUTED`).

Nothing here is wired into Bazel yet: it runs from a checkout with
`bazel`-built inputs, nix for Binaryen and WABT, and Node.

## Layout

| Path | What |
| --- | --- |
| `split/split_link.py` | a reactor's Bazel link (`aquery`) → `link_runtime.sh` and `link_side.sh` |
| `node/` | the dylink loader in JS (`loader.mjs`), and drivers that render, tap every first-frame tap id and write the render stream (`drive_all.mjs`, `hot_run.mjs`); `locrel_fix.mjs` is the loader-side workaround for an unpatched wasm-ld |
| `split/locrel_from_map.py` | the same workaround's slot list, from wasm-ld's `-Map` (`--emit-relocs` crashes lld on large inputs) |
| `profile/` | V8 profile readers: time by module (`prof_by_module.py`), how few functions cover the time (`hot_coverage.py`), what feature code spends its time calling (`feature_calls.py`) |
| `split/native_set.py` | the first native set: functions on profiled stacks plus direct callees (Binaryen's `--print-call-graph`) |
| `split/round.sh` | one round: split, slim, map slots, wasm2c, bridge, build, run, count crossings |
| `split/grow_set.py` | adds what native code called into the interpreter most |
| `split/pick_routed.py` | runtime functions features call that are worth a crossing (time per call) |
| `split/gen_mixed.py` | the bridge: C glue for the wasm2c module (imports, exports, per-signature calls and trampolines, memory over WasmKit's) and a WasmKit shim |
| `split/slim_native.py`, `split/map_slots.py`, `split/wasmtool.py` | the native part without data or unneeded exports; the slots the split added, mapped to the runtime's functions; wasm reading helpers |
| `host/` | SwiftPM hosts on the forked WasmKit: `SideloadCheck` (side modules under WasmKit), `RuntimeCheck` (through Isomer's `WasmKitRuntime.loadSideModule`), `MixedCheck` (mixed mode; its `CHot` target is generated by `round.sh`) |
| `data/` | the Storybook's native set and routed list, as the last round left them |

## Running it

```sh
# 1. The Storybook reactor, and its link split into a runtime and a feature.
cd examples
bazel build -c opt //wasm/example_full_feature:example_full_release.wasm
bazel aquery -c opt 'mnemonic(CppLink, deps(//wasm/example_full_feature:example_full_release.wasm))' \
  --output=jsonproto > /tmp/link.json
python3 ../tools/mixed/split/split_link.py /tmp/link.json full_reactor_release \
  libexample_full_lib.a libstorybook.a example_full_lib.autolink storybook.autolink \
  --out /tmp/linked --wasm-ld <wasm-ld with tools/patches/lld_wasm_pic_locrel.patch>
(cd "$(bazel info -c opt execution_root)" && sh /tmp/linked/link_runtime.sh && sh /tmp/linked/link_side.sh)

# 2. Side modules: the runtime and the Storybook as a side module on WasmKit.
(cd ../tools/mixed/host && swift build -c release --product SideloadCheck)
../tools/mixed/host/.build/release/SideloadCheck /tmp/out.bin /tmp/linked/runtime.wasm /tmp/linked/side.wasm

# 3. Mixed mode, from the saved set (the runtime linked without --strip, so
#    it has names; the split input with only entry points and ROUTED exported).
python3 ../tools/mixed/split/slim_native.py /tmp/linked/runtime.wasm /tmp/split_input.wasm \
  memory,__indirect_function_table,__stack_pointer,iso_hot_start,iso_hot_render,iso_hot_event,iso_hot_alloc,iso_hot_free,@../tools/mixed/data/storybook_routed.txt
RUNTIME=/tmp/linked/runtime.wasm SPLIT_INPUT=/tmp/split_input.wasm SIDE=/tmp/linked/side.wasm \
  BASELINE=<the self-contained reactor's stream, from drive_all.mjs> \
  ROUTED=$PWD/../tools/mixed/data/storybook_routed.txt \
  ../tools/mixed/split/round.sh ../tools/mixed/data/storybook_native_set.txt
```

A new profile: run `node --cpu-prof` over `node/drive_all.mjs` with a named
runtime and side module, then `split/native_set.py` for a first set, then
`round.sh` and `grow_set.py` in turn until the crossings stop falling;
`MixedCheck`'s `COUNT_IMPORTS=1` and `split/pick_routed.py` choose `ROUTED`.

## What it measured (Storybook, 99 taps, every story's page opened)

| | Time | Native code |
| --- | --- | --- |
| Self-contained reactor, WasmKit | 3.15 s | — |
| Mixed mode | 0.44 s | 3.9 MB (7.4 MB with bounds checks) |

The render stream is byte-identical to the self-contained build's in every
configuration. Feature size: the Storybook as a side module is 226 KB gzip,
against 5.4 MB for the reactor; the runtime (6.7 MB gzip) is shipped once.

## Caveats

- The native code relies on WasmKit's guard pages without bounds checks; an
  access out of bounds in native code faults instead of trapping until
  WasmKit's trap handling covers it (the bounds-checked build doesn't).
- The set and routed list come from one workload; a function outside them
  runs interpreted, slower but correct.
- The scripts assume the Storybook's entry points and a scratch directory;
  Bazel rules are the next step.
